1. Consumer sends the request

The external consumer invokes the checkCustomerList SOAP API and sends the request as a SOAP/XML message over HTTP.

The request contains the customer information required for screening, such as customer number, name, nationality, date of birth, residence information, organisation unit, reference information, and the applicable reserve fields.

The consumer should not need to know anything about the internal GRACE architecture or how NetReveal is integrated.

2. SOAP Route receives the request

The request first reaches the check-customer-list route in the GRACE application.

The route acts as the entry point for the API and is responsible for handling the incoming HTTP/SOAP request.

At this stage, the route should mainly coordinate the request flow rather than contain business logic.

The route:

Receives the HTTP request.
Extracts the SOAP payload.
Obtains the correlation ID or creates one if required.
Passes the SOAP payload to the XML parser.
Invokes the appropriate adapter.
Calls the screening service.
Converts the final result into a SOAP response.
Returns the response to the consumer.
3. SOAP XML is parsed

The SOAP request is passed to the XML parser.

The XML parser is responsible only for converting the incoming XML structure into a usable application object.

For example, the SOAP XML may contain fields such as:

kundennummer
name
orgUnitId
staatsangehoerigkeit
geburtsortLand
wohnortStrasse
wohnortOrt
wohnortLand
birthyear
reserve11

The XML parser converts these XML elements into a CheckCustomerListSoapRequest DTO.

At this stage, the application is still dealing with the legacy SOAP contract.

The parser should not decide what reserve11 means or how the customer should be screened. Those responsibilities belong to the adapter/business layer.

4. Adapter transforms the SOAP request into the Canonical Request

The parsed SOAP DTO is passed to the CheckCustomerListAdapter.

This adapter is responsible for isolating the legacy SOAP contract from the internal application model.

It maps the legacy field names to the canonical field names.

For example:

kundennummer          → customerNumber
name                  → name
staatsangehoerigkeit  → nationality
geburtsortLand        → placeOfBirthCountry
wohnortStrasse        → residenceStreet
wohnortOrt            → residenceCity
wohnortLand           → residenceCountry
birthyear             → dateOfBirth
einrichtungsdatum     → creationDate
kundentyp             → customerType
referenz              → referenceNumber

The adapter also handles partner-specific transformation rules.

For example, if a particular reserve field determines whether an additional screening is required, that partner-specific rule is interpreted here and represented in the canonical request.

The result of this step is:

PartnerScreeningRequest

The rest of the application no longer needs to understand the original SOAP field names.

5. Canonical request is passed to the Screening Service

The route passes the canonical request to the PartnerScreeningService.

The canonical model acts as the common contract between the API-specific adapter and the business/service layer.

For example, instead of the service receiving:

kundennummer
geburtsortLand
wohnortOrt
kundentyp

it receives a consistent model such as:

customerNumber
placeOfBirthCountry
residenceCity
customerType

This makes the service independent of the external protocol.

The service is responsible for orchestrating the screening operation.

6. Service prepares the NetReveal request

The screening service passes the canonical request to the NetReveal request mapper.

The mapper converts the internal canonical model into the specific request structure required by NetReveal.

For example:

Canonical customerNumber
        ↓
NetReveal party.id

Canonical name
        ↓
NetReveal party.name

Canonical nationality
        ↓
NetReveal party.nationality

This mapping is kept separate from the service so that NetReveal-specific field names and structures do not leak into the business logic.

The result is a:

NetRevealPartnerRequest
7. NetReveal client sends the request

The service passes the NetReveal request to the NetReveal client.

The NetReveal client is responsible for the actual communication with the downstream NetReveal system.

It handles technical concerns such as:

HTTP request creation
NetReveal endpoint
Authentication
Headers
Timeout
Circuit breaker
Retry, where applicable
Correlation ID propagation
Technical error handling
Logging and monitoring

The service should not directly contain this HTTP communication logic.

The flow is therefore:

Screening Service
       ↓
NetReveal Client
       ↓
NetReveal
8. NetReveal processes the screening

NetReveal receives the request and performs the required screening.

NetReveal returns the screening result to GRACE.

The response can contain information such as:

checkStatus
detailedResult
referenceNumber
reserve15

The checkStatus represents the screening outcome, while fields such as reserve15 can identify the applicable product/result type according to the agreed integration contract.

For example:

checkStatus = GO

indicates that the corresponding screening result is GO.

Similarly:

checkStatus = HOLD

indicates that the result requires further handling according to the business flow.

9. NetReveal response is transformed into the Canonical Response

The NetReveal client returns the NetReveal response to the screening service.

The response is then passed to the NetReveal response mapper.

The mapper converts the NetReveal-specific response into the common canonical response model.

For example:

NetReveal Response

checkStatus = HOLD
reserve15   = 25000

can be represented internally as:

PartnerScreeningResult

status      = HOLD
productType = EMBARGO

Similarly, the applicable reserve15 value can be interpreted according to the product mapping.

This is important because the rest of the application should not need to understand NetReveal-specific codes.

10. Canonical response is returned to the route

Once the response has been transformed, the screening service returns the canonical screening result to the SOAP route.

At this point, the service has completed its responsibility.

The route now has a technology-independent result such as:

status
productType
reference
detailedResult

The route does not need to understand how NetReveal generated that result.

11. Response Adapter transforms the Canonical Response into SOAP Response

The route passes the canonical response to the SOAP response adapter.

The response adapter performs the reverse transformation of the request adapter.

It converts the canonical fields back into the fields required by the legacy SOAP contract.

For example:

status          → checkStatus
reference       → referenceNumber
detailedResult  → detailedResult
productType     → reserve15

The result is a:

CheckCustomerListSoapResponse

This DTO represents what the external SOAP consumer expects.

12. SOAP XML response is generated

The SOAP response DTO is passed to the XML builder.

The XML builder creates the appropriate SOAP envelope and SOAP body according to the agreed SOAP contract/WSDL.

Conceptually:

CheckCustomerListSoapResponse
             ↓
        XML Builder
             ↓
      SOAP Envelope
             +
        SOAP Body

The XML builder is responsible for XML formatting and serialization, rather than business transformation.

13. SOAP response is returned to the consumer

Finally, the SOAP route sends the generated SOAP response back to the consumer.
